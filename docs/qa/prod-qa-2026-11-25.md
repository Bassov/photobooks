## 2. Bugs

### QA-1

**After a redeploy, Preview in an open tab blanks the whole app** — major · chapters: check, site (Preview)

- Seen for real on run 6: the tab was opened before the ~11:45 UTC redeploy, then Preview was pressed. Console: `Failed to load module script: Expected a JavaScript-or-Wasm module script but the server responded with a MIME type of "text/html"`, then pageerror `Failed to fetch dynamically imported module: …/assets/SitePreview-DWojPSnQ.js`. `#root` was empty, the screen blank grey; the editor never came back and Esc did nothing. Reproduced on every later run (runs 7–12, 1280 and DPR 2) with the `stale-chunk` step of `run.mjs`, which serves exactly what prod returns for a missing chunk.
- Server side, reproduced twice by hand: `curl -sD- https://photobooks.photobooks-bassov.workers.dev/assets/SitePreview-DWojPSnQ.js` returns `HTTP/2 200`, `content-type: text/html`, `content-length: 2202` (the SPA `index.html`), not a 404.
- Repro (no deploy needed): open the editor on a book; in DevTools block or rewrite `/assets/SitePreview-*.js` so it returns `index.html` (what prod sends for a missing hash); press **Preview**. Real-life repro: open the editor, deploy a build where the chunk hash changes, press Preview.
- Expected: the app stays usable. Either it reloads once to pick up the new build (after saving), or it shows an error with "Reload". Missing hashed assets should 404, not 200 HTML.
- Actual: white-screen crash of the whole editor. If the book had unsaved edits (the top bar often reads "unsaved" mid-edit), they are at risk.
- Evidence: [23-stale-chunk-blank.jpg](prod-qa-2026-11-25/23-stale-chunk-blank.jpg).
- Likely source: `src/editor/EditorShell.tsx:43` (`lazy(() => import('./SitePreview'))`, the only `lazy()` in `src/`), which has no error boundary and no `vite:preloadError` handler (grep finds neither in `src/`); `wrangler.jsonc:15` `"not_found_handling": "single-page-application"` also answers `/assets/*` misses with `index.html`. Workers (PDF, export, decode) loaded by hashed URL may share the problem; not tested.
- Fix size: M (error boundary + one-shot reload on chunk-load failure, plus a 404 for missing `/assets/*` in the worker or assets config).
- e2e: none (`git grep -l "preloadError\|SitePreview-" e2e` is empty).

### QA-2

**The layout-cycle pill paints over the Settings screen** — minor · chapters: settings, hosting, site-texts

- Repro: open a book, click any spread so the pill "‹ One per page 2/4 ›" shows above it. Gear → Settings, any section (Library, Hosting, Site, Interface).
- Expected: Settings covers the editor; no canvas chrome on it (kit `site-settings`).
- Actual: the pill stays painted on top of the Settings page, at (777, 71) 222×28 at 1440×900, (683, 82) at 1280×800, and next to the "Hosting" and "Interface" headings. `elementFromPoint` at its centre returns `layout-cycle-name`, so it also takes clicks: its ‹ › would change the spread's layout behind Settings.
- Runs: every run since the check was added (runs 7–12 at 1440 @1, 1280×800, 1440 DPR 2), and visible in run 5's screenshots.
- Evidence: [19-hosting.jpg](prod-qa-2026-11-25/19-hosting.jpg), [21-interface-150.jpg](prod-qa-2026-11-25/21-interface-150.jpg).
- Likely source: the pill is rendered in the pasteboard flow, `src/editor/Pasteboard.tsx:611-625`, with `z-index: 20` (`src/editor/LayoutCycle.css:13-17`). It is hidden only for a short gap, asset drag, marquee and `.editor-shell[inert]` (`LayoutCycle.css:43-48`). Settings is opened from `src/editor/EditorTopBar.tsx:431-440` without making the shell inert, and it stacks below the pill.
- Fix size: S (hide the pill while Settings is open, or make the shell inert under Settings as Preview does).
- e2e: none. `e2e/cycle-layouts.spec.ts` and `e2e/kit-layout-cycle.spec.ts` never open Settings.

### QA-3

**Preview opens on a cover without its photo** — minor · chapters: check ("Preview shows the book as the site shows it"), site

- Repro: open a book, click **Cover**, drag a photo from the dock onto the **Front** half (the cover now shows it, see [12-cover-photo.jpg](prod-qa-2026-11-25/12-cover-photo.jpg)). Press **Preview**.
- Expected (guide, chapters "Check before printing" and "Your site"): Preview shows the book as the published site shows it. A published book's closed cover carries its cover photo.
- Actual: the closed book in Preview is the plain cloth colour with the title only. While Preview is open the DOM has no `.cover-front-photo` in the room (the only one is the spread-list thumbnail behind it).
- Runs: 3/3 (runs 5, 7, 10).
- Evidence: [14-preview.jpg](prod-qa-2026-11-25/14-preview.jpg).
- Likely source: `src/editor/SitePreview.tsx:91` builds the room entry with `cover: null`, and `:18` comments "no published cover photo in the preview". The cover slide itself (`PreviewCover`, `:23-31`) would use the tier preview, but the opening closed-book view never gets a cover image.
- Fix size: S–M (pass the editor's cover working-preview URL as the entry cover).
- e2e: none. `e2e/design-r7-panels.spec.ts:350` checks that Preview starts on the cover, not the photo; `e2e/cover-hires.spec.ts` checks the editor cover only.

### QA-4

**Long animation frames while a photo folder loads** — minor (perf; confirm on the CI perf runner before fixing) · chapter: add-photos

- Repro: new book → Photos dock **Add folder…** → a folder with the 10 kit photos, `large-24mp.jpg` (6000×4000) and 3 tiny fixtures. Watch `long-animation-frame` entries (the script logs every LoAF ≥ 200 ms).
- Expected: `.claude/rules/architecture.md` / `src/perf/budgets.ts`: decode off the main thread, zero LoAF in interaction scenarios.
- Actual: every run logged 1–3 LoAF between thumbnails appearing and the dock settling: 219, 210, 227/272/331, 250, 295/205, 213/478/269 ms (runs 5–11, 1440 @1). The UI stays responsive otherwise.
- Caveat: the host was a loaded WSL box (load average up to 43 at the end). Per earlier local-perf notes, frame-budget gates also fail on main locally, so treat this as a lead, not a measurement. Which item triggers it (the 24 MP decode or header read, or the thumb hydrate) is not isolated.
- Likely source: the import path from `src/editor/useChromeImport.tsx:249-265` (`onChoosePhotoFolder`) into the asset read and thumb pipeline (`src/assets/`, `src/editor/thumbCache.ts`).
- Fix size: M (profile first).
- e2e: partial. `e2e/thumb-bulk-hydrate.spec.ts:140` gates LoAF on reload hydrate, not on a first import with a 24 MP photo.

### QA-5

**Console errors for revoked `blob:` URLs** — cosmetic · chapters: place (swap), persistence (reload)

- Seen 3 times in 12 runs, not on demand: run 2 right after the swap drag (place chapter), runs 7 and 8 right after reload + reopening the book. Each time it was `[requestfailed] blob:https://photobooks.photobooks-bassov.workers.dev/<uuid> net::ERR_FILE_NOT_FOUND`, followed by console error `Failed to load resource: net::ERR_FILE_NOT_FOUND`. No visible broken image in the screenshots taken just after.
- Expected: no console errors; an `<img>` should not keep an object URL that was revoked.
- Likely source: an image still pointing at a URL that `src/photo/objectUrlLru.ts:38-92` or `src/editor/thumbCache.ts:130` already revoked (tier swap or LRU eviction while the old `src` is still being fetched).
- Fix size: S–M (repro needs logging of which `img` asks for the revoked URL).
- e2e: none.

### QA-6

**Guide copy: "drag to move" does not hold for photo frames** — cosmetic (guide text) · chapter: frames

- Repro: on a spread with a photo in a frame, press and drag the frame's body (unselected, or selected off the centre grabber).
- Guide (`uikit/src/kit/guide/content.ts:307`): "Click a frame; drag to move, handles to resize".
- Actual, and correct by spec (`openspec/specs/pasteboard/spec.md:116`: "Dragging a filled frame's body … SHALL be this photo drag, never a frame move"): the frame stays put (frame Δ 0,0 on runs 6–12) and the drag is the photo swap drag. An empty frame moves by its body (Δ 60,43). The grabber pans the photo (photo Δ 60,0).
- Expected: the guide says how to move a photo frame (arrows / Position & size, or that only empty frames move by drag).
- Fix size: S (copy in `content.ts:307`; kit guide QA reads that file).
- e2e: n/a (copy).

## 4. Not testable automatically / needs Owner

- **Hosting setup past the token** (chapter 19, steps 2–5): needs a real Cloudflare setup token and domain. Owner: paste a token, choose `books.<domain>`, run "Set up hosting" and check it finishes in about a minute and deletes the token; try "Enter R2 keys yourself".
- **Publish** (chapter 20, steps 2–5): needs hosting. Owner: Publish, "Hide" / Esc while uploading (percentage in the pill), "Published" link, "Open site", drop the network mid-upload and check "Try again" sends only the rest.
- **Published site** (chapter 17, steps 2–3): bookcase home, newest book facing out, ← → and swipe on a phone, Share. Only Preview and the local export were checked here. Owner: open the published site on a desktop and a phone.
- **Real folder picker / permissions**: the run used an OPFS stub, so the native picker, the "Allow" prompt and the regrant after a browser restart were not exercised. Owner: Chrome or Edge, "Create Library" on a real empty folder, restart the browser, reopen.
- **Other browsers**: the "unsupported browser" screen in Firefox / Safari was not checked.
- **Print proof**: the PDFs were checked for existence and size only. Owner: open `exports/*.pdf`, check bleed and crop marks, the cover sheet with spine, and print the 2-up booklet duplex (flip on short edge) and fold it.
- **Relink** (chapter 14, step 2): needs a moved or deleted file on disk between sessions; not set up.
- **Interface size on a 4K screen**: 125 / 150 % only fell back to 100 % at 1440×900 and 1280×800. Owner: check them on a large screen.
- **Open pages / Open cover** buttons: they open files in a new tab; not followed headless.
